To-Do Prioritizer: What I'd Measure and How I'd Experiment

A data-driven analysis of what metrics matter, how to instrument the product, and three A/B experiments I'd run to improve task completion rates — written as if the app had 1,000+ active users.

Author
Nicole Surawski
Product
To-Do Prioritizer
Assumed Scale
1,000+ MAU
Date
March 2026

Context

The To-Do Prioritizer is a task management tool that scores tasks across urgency, importance, and effort using a weighted formula, then auto-categorizes them into High, Medium, and Low priority. Users can adjust weights via presets (Balanced, Deadline-driven, Impact-first, Quick wins).

This document defines the metrics framework and experimentation plan as if the product had 1,000+ monthly active users. The goal is to demonstrate how I'd use data to identify friction, validate hypotheses, and make product decisions — not just ship features.

The central question: Does scoring and ranking tasks actually help people complete more tasks, or does it just help them organize tasks? The entire metrics framework is designed to answer this.

North Star Metric

North Star

Weekly Task Completion Rate

% of tasks marked complete within 7 days of being scored. This measures whether prioritization drives follow-through, not just organization. A user who scores 10 tasks and completes 7 has a 70% WCR.

Why this metric: Task creation measures engagement but not value. Task completion measures whether the product delivers on its promise: helping you do the right things, not just list them. The 7-day window captures most natural task lifecycles while excluding stale backlog items.

Metrics Framework

Organized into four tiers — each serves a different decision-making purpose:

Primary Metrics (Product Health)

Primary

Scoring Adoption Rate

% of added tasks that get scored (moved from "Unprioritized" to a priority bucket). Target: ≥ 75%. If users add tasks but don't score them, the core value prop isn't landing.

Primary

D7 Retention

% of new users who return within 7 days. Target: ≥ 40%. First session is curiosity; second session is adoption. This tells us whether the product earns a spot in the user's workflow.

Primary

Session Frequency

Average sessions per active user per week. Target: ≥ 3. A task manager that's opened less than 3x/week isn't embedded in the daily workflow.

Secondary Metrics (Feature Engagement)

Secondary

Preset Exploration Rate

% of users who try at least 2 weight presets. Validates that context-aware weighting is a real need, not a feature for its own sake.

Secondary

Subtask Adoption

% of tasks with at least 1 subtask. Measures demand for task decomposition. Informs whether to invest more in subtask UX in v2.

Secondary

Manual Override Rate

% of scored tasks that get manually reordered via drag-and-drop after scoring. High override rate (> 30%) suggests the scoring model doesn't match user judgment — a signal to revisit the formula.

Secondary

Celebration Trigger Rate

% of sessions where all tasks are completed (triggering confetti). Low rates may mean users add tasks faster than they complete them — the list grows but never empties.

Guardrail Metrics (Things That Should NOT Change)

Guardrail

Time to First Task

Seconds from page load to first task added. Should stay under 15 seconds. If an experiment increases scoring adoption but slows down initial task entry, it's a net negative.

Guardrail

Task Deletion Rate

% of tasks deleted (not completed). Should stay under 15%. A spike in deletions after a change could mean users are frustrated, not organized.

User Funnel

The critical conversion path with expected drop-off at each stage:

Stage Action Expected Rate Drop-off Signal
1. Land User opens the app 100% —
2. Add Creates first task ~85% If < 70%: onboarding is confusing or value prop is unclear
3. Score Opens scoring panel and saves a priority ~55% If < 40%: scoring panel is too complex or not discoverable
4. Organize Scores 3+ tasks (enough to see ranking in action) ~40% If < 25%: scoring doesn't feel worth the effort per task
5. Complete Marks at least 1 scored task as done ~35% If < 20%: tool helps organize but doesn't drive action
6. Return Comes back within 7 days ~25% If < 15%: product is interesting but not habit-forming
The biggest drop-off risk: Stage 2 → Stage 3 (Add → Score). Users add tasks easily, but the scoring panel requires opening a sub-UI, setting 3 inputs, and saving. This is the friction point most likely to kill adoption — and the focus of Experiment #1 below.

Instrumentation Plan

Key events I'd log to power the metrics above. Each event includes the minimum properties needed for analysis:

Event Name Trigger Properties
task_added User creates a new task session_id, task_count (total tasks), time_since_session_start
scoring_panel_opened User clicks the prioritize button on a task task_id, task_status (unprioritized/active)
task_scored User saves a priority score task_id, score, priority (high/med/low), importance, effort, has_due_date, time_in_panel
task_completed User marks a task as done task_id, priority, time_since_scored, was_high_priority
task_deleted User deletes a task task_id, was_scored, priority
preset_applied User selects a weight preset preset_name, previous_preset, scored_task_count
task_reordered User drags a task to a new position task_id, from_section, to_section, was_scored
celebration_triggered All tasks marked complete total_tasks, session_duration, scored_task_count

Three Experiments I'd Run

Each experiment targets a specific conversion point in the funnel, has a clear hypothesis, and defines success criteria upfront.

Experiment 1

Inline Scoring vs. Panel Scoring

Funnel Stage: Add → Score Medium Effort High Expected Impact

Hypothesis: The current scoring panel (a separate expandable UI below each task) creates too much friction. If we let users score tasks inline — directly on the task row — more users will score their tasks, increasing the Scoring Adoption Rate.

Control (A)

Current behavior: click a button to open a full scoring panel below the task. Set due date, importance (1-5 dots), effort (1-5 dots), see live preview, click "Save Priority."

Variant (B)

Inline scoring: when a user adds a task, three compact inputs appear directly on the task row — a small date picker, a 1-5 importance selector, and a 1-5 effort selector. Score calculates and displays in real-time. No "Save" button; values persist on change. The full panel is still available for users who want the detailed view.

Success Criteria
  • Primary: Scoring Adoption Rate increases by ≥ 15 percentage points (e.g., 55% → 70%)
  • Secondary: Time-to-first-score decreases by ≥ 30%
  • Guardrail: Task Completion Rate does not decrease (inline scoring shouldn't make tasks feel "done" just because they're scored)
  • Guardrail: Time to First Task stays under 15 seconds
Expected Duration & Sample Size

At 1,000 MAU with ~500 weekly active users, a 50/50 split gives 250 users per group. With a baseline scoring rate of 55% and MDE of 15pp, we'd need ~2 weeks to reach 95% statistical significance (80% power).

Why this experiment matters: The Add → Score drop-off is the biggest hole in the funnel. If users don't score tasks, the entire scoring model is invisible — and the product is just another to-do list. Reducing friction at this step has the highest leverage on downstream metrics.
Experiment 2

Smart Defaults: Auto-Suggest Importance and Effort

Funnel Stage: Score → Organize Medium-High Effort Medium Expected Impact

Hypothesis: Users who score 1-2 tasks but stop before 3 do so because scoring each task feels repetitive. If we auto-suggest importance and effort values based on the task title (using keyword matching or a simple heuristic), users will score more tasks because the inputs are pre-filled and they just need to confirm or adjust.

Control (A)

Current behavior: importance defaults to 3 and effort defaults to 3 for every task. Users must manually evaluate and set each value.

Variant (B)

Smart defaults: the app pre-fills importance and effort based on simple keyword heuristics:

  • Keywords like "urgent," "deadline," "ASAP," "client" → importance: 5
  • Keywords like "quick," "small," "simple," "email" → effort: 1-2
  • Keywords like "research," "plan," "redesign," "migration" → effort: 4-5
  • All other tasks → defaults to 3/3 (same as control)

Pre-filled values are visually distinguished (e.g., lighter dot color) so users know they can adjust them. A small "suggested" label appears next to auto-filled values.

Success Criteria
  • Primary: % of users scoring 3+ tasks increases by ≥ 10 percentage points
  • Secondary: Average time spent in the scoring panel decreases by ≥ 20%
  • Guardrail: Manual Override Rate stays below 40% (if users are constantly changing suggestions, the heuristics are wrong and adding friction, not removing it)
  • Guardrail: Score accuracy — the distribution of final scores should not collapse (i.e., smart defaults shouldn't cause all tasks to cluster at the same priority)
Expected Duration & Sample Size

Same 50/50 split at 1,000 MAU. With a smaller expected effect size (10pp), we'd need ~3 weeks to reach statistical significance.

Why this experiment matters: Scoring 3+ tasks is the threshold where the ranking model becomes useful (you need enough data points for prioritization to be meaningful). If we can push more users past this activation point, downstream retention and completion metrics should improve as a second-order effect.
Experiment 3

Focus Mode: Show Only the Top 3 Tasks

Funnel Stage: Organize → Complete Low Effort Medium Expected Impact

Hypothesis: Users with 10+ scored tasks still experience decision fatigue because the full ranked list is visible. Seeing 15 tasks — even ranked — is still overwhelming. If we offer a "Focus Mode" that shows only the top 3 tasks (hiding everything else), users will complete more tasks per session because the visible scope feels manageable.

Control (A)

Current behavior: all tasks visible, grouped into High / Medium / Low sections with full scrollable list.

Variant (B)

A toggle at the top of the task list: "Focus Mode." When enabled:

  • Only the top 3 highest-scored tasks are visible
  • A subtle "and X more tasks" indicator shows below
  • When a task is completed, the next-highest task slides in
  • The progress bar still reflects total tasks, so users see overall progress
  • Focus Mode persists to localStorage so it stays on across sessions
Success Criteria
  • Primary: Tasks completed per session increases by ≥ 20% for users with 10+ tasks
  • Secondary: Celebration Trigger Rate increases (more users complete all tasks)
  • Guardrail: Users don't delete more tasks (hiding tasks shouldn't cause users to forget about them)
  • Guardrail: Users don't disable Focus Mode within 60 seconds (which would signal it's more annoying than helpful)
Expected Duration & Sample Size

This experiment targets a subset (users with 10+ tasks), reducing the eligible population. At 1,000 MAU, ~300-400 users likely have 10+ tasks. A 50/50 split with 150-200 per group needs ~4 weeks to reach significance.

Why this experiment matters: This tests a fundamental product philosophy question: does showing less drive more action than showing everything ranked? If Focus Mode wins, it suggests that prioritization value comes from narrowing scope, not just ordering tasks. That insight would reshape the product roadmap toward constraint-based design.

Experiment Prioritization

Experiment Funnel Impact Build Effort Learning Value Run Order
1. Inline Scoring High Medium High First — largest funnel gap
3. Focus Mode Medium Low High Second — cheap to build, high learning value
2. Smart Defaults Medium Medium-High Medium Third — depends on Experiment 1 results
Sequencing logic: Run Experiment 1 first because the Add → Score drop-off is the biggest funnel gap — fixing it has the highest leverage. Run Focus Mode second because it's cheap and the learning (does less = more action?) informs the entire product direction. Run Smart Defaults last because its value depends on how many users are reaching the scoring panel after Experiment 1.

What I'd Do With the Results

If Experiment 1 wins (Inline Scoring)

  • Ship inline scoring as the default experience
  • Keep the full scoring panel as an "Advanced" option for power users
  • Revisit the scoring formula — with more users scoring, we'll have enough data to evaluate whether the 3-factor model is sufficient or if we need a 4th factor

If Experiment 1 loses

  • The problem isn't friction — it's motivation. Users can find the scoring panel but don't see enough value
  • Next move: test showing a "before/after" comparison (your unranked list vs. your prioritized list) to make the value of scoring more tangible

If Experiment 3 wins (Focus Mode)

  • Make Focus Mode the default for users with 10+ tasks
  • Explore a "daily planning" workflow: each morning, the app presents your top 3 and asks "Is this your plan for today?"
  • This validates the thesis that the product should be opinionated about what to show, not just rank everything

If Experiment 3 loses

  • Users want the full picture, not a constrained view — the value is in the ranking itself, not in hiding lower items
  • Invest instead in better visual hierarchy (make the top task dramatically more prominent without hiding others)

Key Takeaway

Good PM experimentation isn't about testing random ideas — it's about testing hypotheses that change how you think about the product. Each experiment above isn't just "does this feature work?" — it's a question about user behavior. Does reducing friction increase engagement? Does showing less drive more action? Does pre-filling inputs help or hurt? The answers to these questions shape not just the next feature, but the product strategy.
