Why This Document Exists

Most PM portfolios showcase solo artifacts — PRDs, teardowns, metrics docs. But product management is fundamentally a team sport. This document shows how I'd take a feature from insight to shipped product by working across functions.

I chose Focus Mode because it originated from the metrics & experimentation write-up I built for the To-Do Prioritizer. It was the highest-impact A/B experiment I designed, making it a natural candidate for a full cross-functional spec.

What this demonstrates: Stakeholder alignment, design collaboration, engineering scoping, launch coordination, decision-making under constraints, and clear async communication.

1. Stakeholder Alignment

Before writing a single requirement, the first job is to align stakeholders on why this feature matters and what success looks like. Here's how I'd frame the opportunity.

The Problem (Framed for Leadership)

Users add tasks to the To-Do Prioritizer, but completion rates plateau after the first week. Our funnel data shows a 40% drop-off between "task scored" and "task completed." Users tell us the prioritized list is helpful but overwhelming — they don't know where to start when they have 15+ active tasks.

The Hypothesis

If we surface a focused view of a user's top 3 tasks for the day, then weekly task completion rate will increase by 15%, because reducing the visible scope lowers decision fatigue and creates a clear starting point.

Why Now?

  • Retention signal: Users who complete 3+ tasks/week retain at 2x the rate of those who complete fewer. Focus Mode directly targets this behavior.
  • Low technical risk: The scoring engine already exists. Focus Mode is a presentation layer change, not a new algorithm.
  • Competitive gap: Todoist and TickTick have "Today" views but no intelligent prioritization. This combines both.

What I'd Ask For in the Kickoff

QuestionWhy It MattersExpected Answer
Are we optimizing for completion rate or engagement time? These can conflict — Focus Mode reduces time-in-app but increases completions Completion rate (aligns with North Star)
Can we ship this as an A/B test first, or does leadership want a full rollout? Affects scope, timeline, and whether we need a feature flag system A/B test first with 50/50 split

2. Design Collaboration

I don't hand designers pixel-perfect mockups — I hand them constraints, context, and user problems. Here's the design brief I'd share.

Design Brief: Focus Mode

DB
Design Brief
Shared in: #design-reviews channel • Async-first, sync follow-up if needed

User problem: Users with 10+ tasks feel overwhelmed by the full list. They've told us "I know the app ranked everything, but I still don't know what to do first today."

What we need: A focused view that shows only the top 3 tasks for today, accessible from the main task list without losing context of the full backlog.

Constraints:

  • Must work within the existing layout (no new pages or navigation changes)
  • Must be accessible via keyboard shortcut and toggle button
  • Users must be able to exit Focus Mode without losing their place
  • Dark mode support required (existing CSS variables should handle this)

What I'm NOT specifying: Visual treatment, animation, iconography, exact placement of the toggle. Those are design decisions. I've included a rough wireframe sketch below to communicate the concept, not the solution.

Open questions for design:

  • Should completed tasks in Focus Mode animate away and pull in task #4, or should the user see "2 of 3 done" as a progress signal?
  • Is there a way to make the transition between list view and Focus Mode feel lightweight rather than like a mode switch?

Design Decisions I'd Defer vs. Own

DecisionOwnerRationale
How many tasks to show in Focus Mode PM Product decision tied to the hypothesis (3 tasks reduces overwhelm). Would revisit based on experiment data.
Visual treatment of the focused view Design Design has context on visual hierarchy, spacing, and consistency with the design system.
Animation and transition behavior Design Interaction design is a design discipline. I provide the functional states; design decides how to move between them.
Whether Focus Mode is opt-in or default PM Directly affects the experiment design and metrics. Starting as opt-in via toggle for the A/B test.
Keyboard shortcut binding Engineering Engineering knows what shortcuts are already in use and what's conventional for the platform.

3. Engineering Scoping

I believe PMs should come to engineering scoping with a clear problem and flexible solution space — not a spec that treats engineers as implementers. Here's how I'd approach the technical discussion.

Pre-Scoping: What I'd Prepare

  • Functional requirements doc (what Focus Mode needs to do, not how to build it)
  • Edge cases list (what happens with 0 tasks? With all tasks completed? With tasks added mid-focus?)
  • Priority tiers so engineering can propose scope cuts if needed

Requirements by Priority

PriorityRequirementNotes for Eng
P0 Toggle between full list and Focus Mode (top 3 tasks by score) Core feature. Scoring logic already exists — this is a filter, not a new algorithm.
P0 Mark tasks complete from within Focus Mode Should use existing completion handler. No new state management needed.
P0 Persist Focus Mode preference in localStorage If user prefers Focus Mode, it should be the default on next visit.
P1 Progress indicator ("2 of 3 completed today") Design-dependent. May be a simple counter or a visual progress bar.
P1 Keyboard shortcut to toggle Focus Mode Nice-to-have for power users. Eng picks the binding.
P2 "Why these 3?" tooltip explaining the scoring rationale Builds trust in the prioritization. Defer if it adds significant scope.
P2 Celebration micro-interaction when all 3 tasks are completed Engagement driver but not core value. Cut first if scope is tight.

Questions I'd Ask Engineering

My approach: I come to scoping with questions, not answers. Engineers know the codebase. My job is to make sure they have enough context to make good technical decisions.
  • "The scoring engine re-ranks on every task change. In Focus Mode, should we snapshot the top 3 at the start of the day, or re-rank dynamically? What are the tradeoffs?"
  • "What's the simplest way to implement the feature flag for the A/B test? Do we already have a pattern for this, or would we need to build one?"
  • "I scoped this as 2 sprints for P0 + P1. Does that feel right, or am I off? What would you cut to fit it in 1 sprint?"
  • "Are there any accessibility concerns I should flag in the design brief? I want to make sure Focus Mode works with screen readers."

Decision Log: Scoping Tradeoffs

These are the kinds of decisions that come up in scoping sessions. I document them so the team can reference them later and so stakeholders understand why certain choices were made.

Should Focus Mode re-rank dynamically or snapshot at start of day?
Options: (A) Dynamic re-ranking on every change, (B) Snapshot top 3 at midnight/first open, (C) Snapshot but allow manual refresh
Decision: Option C — Snapshot with manual refresh
Rationale: Dynamic re-ranking would be disorienting ("my #2 task just disappeared"). A static snapshot is predictable. Adding a refresh button gives users control without complexity. Engineering confirmed this is the simplest implementation.
Should completing all 3 focus tasks auto-exit Focus Mode?
Options: (A) Auto-exit to full list, (B) Show "all done" state with option to add more, (C) Pull in task #4-5-6 automatically
Decision: Option B — "All done" state
Rationale: The point of Focus Mode is to create a sense of completion. Auto-pulling in more tasks defeats that purpose. The "all done" state reinforces the accomplishment and lets the user choose whether to continue.
Should we build a feature flag system or use a simpler approach for the A/B test?
Options: (A) Build a reusable feature flag system, (B) Simple localStorage-based random assignment, (C) Use a third-party service (LaunchDarkly, etc.)
Decision: Option B — localStorage random assignment
Rationale: We only need one experiment right now. Building a full feature flag system is over-engineering. A localStorage coin flip on first visit is 10 lines of code and sufficient for a 50/50 split. We'd revisit if we run 3+ concurrent experiments.

5. Launch Timeline

Here's the 6-week plan I'd propose. Each week has a clear deliverable, a responsible party, and a checkpoint.

Week 1 — Alignment
Kickoff + Design Brief Handoff
PM shares design brief and requirements. Engineering reviews for feasibility. Design starts exploration. Checkpoint: Async Loom review of the brief with all stakeholders.
Week 2 — Design
Design Review + Engineering Scoping
Design presents 2-3 concepts. PM and Eng provide feedback. Engineering finalizes sprint plan and identifies technical risks. Checkpoint: Design decision documented, sprint backlog created.
Week 3-4 — Build
Sprint 1: Core Focus Mode (P0 Requirements)
Engineering implements toggle, filtered view, completion handling, and localStorage persistence. PM writes QA test cases and preps analytics event specs. Checkpoint: Mid-sprint demo of working toggle.
Week 5 — Polish
Sprint 2: P1 Items + Feature Flag + Analytics
Progress indicator, keyboard shortcut, A/B test infrastructure, and analytics instrumentation. PM begins drafting the stakeholder update template. Checkpoint: Feature flag working in staging, analytics events firing.
Week 6 — Launch
QA, Soft Launch, and Monitoring
Full QA pass on both variants. Gradual rollout: 10% → 50%. PM monitors key metrics daily for the first week. Checkpoint: Go/no-go on full 50% split after 48 hours of clean data.

Result: Ship It

After 2 weeks at 50% traffic, Focus Mode users show:

  • +18% weekly task completion rate (target was +15%) — statistically significant at p < 0.01

What surprised us: Users in Focus Mode actually added more tasks than control, not fewer. Hypothesis: completing tasks creates momentum to add new ones. Worth exploring in the next experiment cycle.

7. How I'd Run the Retro

After shipping, I'd facilitate a lightweight retrospective focused on process, not just outcomes. Here's the format I prefer.

Retro Format: Start / Stop / Continue

CategoryExample Prompts I'd Seed
Start
  • Should we start writing design briefs for all features, or was this overkill?
  • Should we start using a shared decision log for all projects?
Stop
  • Was the weekly status update useful, or did it feel like overhead?
  • Did the RACI cause confusion or help?
Continue
  • Async-first communication (no recurring meetings for this project)
  • Scoping sessions with explicit tradeoff documentation
Why I include the retro: Shipping the feature is only half the job. The other half is making the next project better. A PM who doesn't close the loop on process is leaving improvement on the table.
